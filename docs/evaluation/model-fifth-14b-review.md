## 超时原因与资源证据

整批墙钟 **749.187 秒**，未触及 900 秒全局截止；加载 **17.886 秒**，canary **16.301 秒且通过**。采样到 server VmHWM 峰值 **15,161,836 KiB，约 14.46 GiB**，这是 server 进程指标，不能当成整个 runner 的内存峰值或安全余量。

日志有一个推理槽位 `n_slots=1`，五次约 120 秒客户端超时分别对应任务 43、125、198、325、349 的 `cancel task`；前一任务取消并释放后才启动下一任务，释放至下一次启动约在 0.1 秒内。**未见前面请求遗留运行、累积排队拖慢后续请求的证据。** 日志能看见被取消任务已经处理过 token，却没有保留这些任务的生成文本，因此不能凭 token 数推断它们将答对、答错或拒答。

七次槽位释放（canary、五次取消、第六项完成）均记录 `truncated=0`。全部输入预算也通过：最大 `842 + 700 + 8 = 1550`，明显低于 4096。现有证据不支持 context 溢出或 700 tokens 上限耗尽导致本次失败；五个请求在返回完整非流式响应前被 120 秒请求截止取消。不能把日志的 `truncated=0` 误写成五项完整输出，更不能为缺失正文补一个 `finish_reason`。

保留日志没有 OOM、崩溃或服务器重启记录；随后第六项成功返回，最后有正常清理信息。没有 kernel/系统日志，不能额外宣称已测得整机 OOM 安全余量。控制项实际 prefill **55.462 秒**、生成 **32.119 秒**，生成 116 tokens，约 **3.58 tokens/s**；只代表这次较短控制输入，不能用于插值预测其他模型、长正文或整个批次的表现。

## 是否值得考虑 8B

**有有限的探索依据，但没有 8B 能成功交付或语义达标的证据。** 4B 单步曾完整返回却出现第三方主语、依赖入口、字段角色和无依据费用问题；4B 两步仍没有得到完整可用中文介绍。14B 这次则没有产生可比较的有来源语义输出，只证明当前更大资产在既定 CPU/120 秒协议下交付失败。两个端点不能证明质量或速度随参数量平滑变化。

若仍要判断免费 CPU 自动解读这条路径，**最多再做一次固定协议的 8B 资产对照具有诊断价值**：沿用当前已审 v3、相同六项和全部原时限，独立核实官方资产与许可，不再围绕六项修改 prompt，也不先消耗隐藏验收材料。这只是填补尚未实测的资源/能力区间，不能承诺比两端更好；量化差异也必须记录。出现同类重大语义错误或仍不能按期返回，就应停止在这六项上继续选型调参，把自动解读保留为未验证研究项，产品内容依靠已有可核实证据与审阅链路。

不建议根据本次结果直接放宽 14B 请求时限、绕过失败保存、降低验证标准或宣布可进入生产。V4 的工程与内容交付判断应继续独立于模型研究结果。
